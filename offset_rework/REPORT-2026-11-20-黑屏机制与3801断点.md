关键：`3801` 是登录后第 52–65 秒才发的包，**根本不在这条时间线上**。改 3801 前后黑屏率没有变化（改之前 12:04/12:07/12:10 也黑）。所以两个问题是**独立的**。

## 二、黑屏的实测机制：客户端开机有一段"单线程重活"

对黑屏局做进程级采样（每秒 1 次，抓 CPU 与累计读字节）：

- 出窗口前有 **约 27 秒单核 100% 死转**（每 3–4 秒墙钟烧 3–4 秒 CPU）；线程数恒定 80，**没有任何 TCP 连接**；
- 同期磁盘读持续在 **300–540 MB/s**，整段累计约 5–6 GB；
- 窗口在 t≈41s 才出现，线程数从 80 跳到 137。

对照：能出标题的局，`local_platform_config` 在 5.9s 就完成了，整段没有这段重活。

**结论（已验证）**：黑屏 = 客户端开机阶段有一段单线程的加载/校验重活，跑得慢时整条启动链被推迟约 13–22 秒；一旦 `account_loaded` 落到 37–38 秒，客户端就**不再创建标题界面**（钩子 `0x4aa94a0` 从未被调用），只剩心跳，画面永久黑。

**判据（已验证）**：`native_account_loaded` ≈ **24.3–24.6s → 出标题**；≈ **37.3–38.4s → 黑屏**。中间没有第三种。

**推测**：这段重活是一次"资产/着色器缓存冷读"，受机器瞬时负载（包括我自己跑的采样脚本、抓图、多开进程）影响，所以同一套代码会时快时慢。

## 五、真正卡住"进阿尔比恩"的断点：proc 3801 无应答

被踢前最后 2 秒的原始包（同一批 `20000` 子请求，`request_id` 20–24）：

```
request_id 23 → 3651 → account_collection personal_world_events → response 20000
request_id 24 → 3801 → game_request            ← 服务端收到了
（既没有 account_collection，也没有 response）   ← 应答没产出
→ ClientService connection_rejected  "truncated payload"  request_id=24
```

其它 22 条子请求全部有对应 `account_collection`，只有 3801 什么都没有，且拒绝发生在**同一毫秒**（0ms），说明不是编码慢，是**直接被判空/立刻抛错**。

客户端侧期望结构（`unpacked/assets/network-expansion.json`）：
`M1Response_JumpingPeriodVaild { size=4, fields=[Notification:i32] }`。

### 三次修复尝试（全部失败，均已实测）

| 方案 | 结果 | 原因 |
|---|---|---|
① 集合名编成 `jumping_period_vaild` | 空包 / 被踢 | `characters.sqlite3` 的 `account_collections.collection_key` 有 CHECK 白名单（48 个名字），**没有这个名字** |
② 改指白名单内 `content_clock` | 空包 / 被踢 | 该行 `value_json` 里没有 `Notification` 字段；其规范 schema 是 `CheckedAt/EventIds/BattlePassIds`，与声明不符 |
③ 改指 `inventory_revision`（规范 schema 就是单个 i32，行存在）| 仍 0ms 空包 | 服务端**根本没查**我改的 `GAME_COLLECTIONS` 这一份表，说明派发表在别处（模块内另有拷贝/类内表） |
