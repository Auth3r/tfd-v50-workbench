## 2. 11-20 凌晨新增的三条硬结论

### 2.1 `TFD_TRIM_COUNT=1` 实验：1 条也读成 0
- 新增钩子 `_limit_characters(LS)`（`patch_v50.py`），环境变量 `TFD_TRIM_COUNT=N` 把 `CharacterList` 截成前 N 条。
- 实机：`LIMIT 36 -> 1 (db=36)`，客户端仍 `character_count 0, creation_required true`（run `20261119T183941-f799e8`）。
- 意义：**不是条数问题**。要么新版根本没读这个数组，要么读完被过滤掉。

### 2.2 `LauncherEventRouter is not defined` 是我们自己造成的，且历史全程存在
- `patch_v50.py` 的 `fake_rt()` 把所有 `tools/*.js` 一律替换成 `// skipped`，其中就包含 `tools/launcher_event_router.js`（它负责定义 `LauncherEventRouter`）。
- 该报错从 11-18 起**每一局都有**，包括旧客户端跑通进世界那几局 → **无害，不要再当线索**。
- 如需消除：把 `fake_rt` 里 `'// skipped'` 改成只跳过不需要的那几个，或者补一行 `var LauncherEventRouter = ...` 的空壳定义。属于"降噪"，与主线无关。

### 2.3 启动器的协议表是"名字+类型"的 DSL，可读可枚举
`login_server` 暴露的 schema 变量都是 `list[(字段名, 类型)]`，例：
```
GAME_ACCOUNT_REQUEST = [('AccountUid','i64')]
ACCOUNT_SIMPLE       = [('Uid','i64'), ('Name','string'), ('LoginPlatformId','string'), ...
                        ('WearingList', ('array', [('SocketIndex','i32'), ...])), ...]
LOGIN_REQUEST        = [('name','string'), ('ExternalLinkerType','u8'), ...]
PRIVATE_WORLD_RESPONSE / HANDSHAKE / TITLE_INVENTORY / INVENTORY_SLOT_REQUEST /
INVENTORY_SLOTS / JOIN_DEDICATED / JOIN_DEDICATED_RESULT / OPTION_PRESET /
BOOST_EFFECTS / JUNK_ITEM_FILTER / JUNK_ANCESTOR_FILTER / DEDI_OID ...
```
类型记号：`i64/u8/i32/i16/float/bool/string/ticks/raw32` + `('array', [元素 schema])` + 嵌套 `[...]`。

四张分发表（`TFD_PROBE_HANDLERS=1` 打印）：
- `GAME_COLLECTIONS` = [411,117,121,123,124,604,608,701,710,801,1004,1010,1558,1702,1705,1708,2201,3100,3400,3651]
- `GAME_MUTATIONS` = [3407,3412,11001,11002,11003,11005,11006,11007]
- `GAME_ONEWAY` = [1006,1007]
- `PROGRESSION_REQUESTS` = [1004,1010]
- **`2006` 不在任何一张表**：创角请求不是走这些分发表的，需要在 `login_server.serve` 的收包循环里找（或在 `LocalService`）。

## 5. 已排除假设（不要再试）

1. 服务端空账号 / 数据缺失 —— `Store.list_characters(1)` 返回 36，快照完整。
2. 结构体变化 —— 两版 `M1AccountSimpleInfo` 均 size=0x118 / 35 字段 / id=0x4500000023；`M1CharacterSimpleInfo` 均 size=0x50 / 8 字段 / id=0x4500000004；字段名与顺序逐项一致。
3. 字段名对不上 —— 新版读出 `Uid/CharacterTid/Level/MaxLevel/EigenFactorLevel/Favorites/SelectedLoadoutSlotIndex/Customizes`，与旧版一致。
4. 类型宽度变化 —— `CreatedTime` 两版都是 0x19（64 位）。
5. 变长编码 —— 撑到 `1<<40` 仍 0。
6. 删/改字段 —— 只留 `CharacterTid` → `connection_rejected`；删 `CombatPower/CreatedTime/PlayTime` → `0xC0000005`。
7. 请求号不同 —— 登录阶段两版 procedure 完全一致；`30004` 是 5 秒心跳，不是"每角色一次"。
8. 条数太多 —— **`TFD_TRIM_COUNT=1` 仍 0**（本文件 2.1）。
9. 桥装错 —— 已按 sha 自动选桥。
10. `LauncherEventRouter` 报错 —— 我们自己造成的，历史上全程存在（本文件 2.2）。

## 9. 03:0x ~ 03:5x 的颠覆性更新（必读）

### 9.1 决定性发现：桥读的是死字段 `+0x70`，新版角色数在 `+0xB8`
- 用 `hexdump` 探针（`old_bridge_v8_probe_hexdump.js`）在 `0x44a5370` 的 `onEnter` 里 dump 账号对象（`a[1]`，uid 读出来 = 1 ✔）：
  - `+0x00` = `Uid`(i64) = 1
  - `+0x08` = 指向 UTF-16 字符串 `demo`（`64 00 65 00 6d 00 6f 00`）→ `Name` 指针
  - `+0x10` = 5（长度）、`+0x14` = 8（容量）
  - `+0x40` = 指针、`+0x48` = 8 → `WearingList`（8 条，与快照 shape `list[8]` 完全对上）
  - **`+0x70` = 0（旧桥一直读这里 → 恒 0，就是"36 角色被读成 0"的全部真相）**
  - `+0xB0` = 指针、**`+0xB8` = 0x23 = 35**、`+0xBC` = 0x28 = 40（40 正好是 1 号角色 Lv40/Max40）
  - `+0x80 / +0x88` = 0 / 0（旧桥的 mastery 读数位置，同样是死字段；真值 14 / 350010 读不到）
- 同一局服务端 TRACE 铁证：`Store.list_characters(1)` 返回 **36** 条、`selected_character(1)=23`、`load_mastery(1)={Level:14, Exp:350010, Revision:229}`，`account_snapshot` shape `CharacterList list[36] / SelectedCharacter 23 / MasteryRankLevel …`。→ **服务端一个字节都没少，全是桥读错了位置。**

### 9.2 改读 `+0xB8` 后的实机结果
- 新桥 `old_bridge_v9_count_b8.js`（两处 `a[1].add(0x70)` 都换成 `0xb8`）：
  - `native_account_loaded {"character_count": 35, "creation_required": false}`（run `20261119T192854-23c2f5`、`193900-1aa0c7`）
  - 客户端**不再进"请选择你的继承者"创角页**
- 但 **35 ≠ 36**：`+0xB8` 到底是"角色数"还是别的计数（少 1 条）仍未确认；`+0xB0` 指向的并不是角色数组（dump 出来是一片 `Fortress_GroundModule…` 字符串池）。
- mastery 仍读 `0`：`+0x80/+0x88` 也是旧偏移，新版要重新定位。

### 9.3 但这之后画面还是黑的 —— 真问题浮出水面：**UI 页面根本没建起来**
- `old_bridge_v10_title_probe.js`（在 `0x4aa94a0` 标题回调里打 gate 状态）：**一次都没触发**。
- `old_bridge_v11_page_probe.js`（在 `0x4aa36b0` 页面切换里打页面号）：**一次都没触发**。
- 角色注册观察点 `0x40f8c10`（旧版进游戏时逐个注册 36 个角色、事件 `native_character_registered` 36 次）：**新版一次都没触发**。
- 也就是说：新版客户端**既没有页面切换、也没有角色注册**，它停在最早期的状态；
  我们能连上 LoginService 全是因为桥里的 `probe_direct_login` 强制直连（`0x449d540` 里 22 秒后 `login(obj,ticket)`），UI 完全没参与。
- 客户端**确实在渲染**：GPU Engine `engtype_3d` 采样 42%~73%（pid 对应的 3D 引擎持续占用），但画面纯黑 → 渲染循环在跑、场景/页面是空的。

### 9.4 控件池普查（为新版 UI 找路）
- `base+0xb89c280`（chunks 指针）/ `base+0xb89c294`（数量）在新版**依然有效**：数量从 3.6 万一路涨到 **约 25 万个控件**。
- 控件的 `type` 指针在 `obj+0x10`，`type+0x38` = 类深度；实测深度分布以 **1 / 3** 为主，另有 2 / 4 / 5，**最大只到 5**。
- `lobbyClass()`（`0x38e1390`）返回的类：`klass=0x181e2ec0`、`klass+0x30=0x18079d80`、`klass+0x38=6`。
- 两个失败的尝试（记录以免重走）：
  1. 直接对任意控件调 `widgetOwner()`（`0x4acf6c0`）→ **900 次调用全抛异常**，不能乱调。
  2. 用"类继承链里是否含 `klass+0x30`"筛（扫 2 万个控件）→ **命中 0**。说明要么新版大厅类的深度不是 6（实测没有深度 6 的控件），要么 `type+0x30` 的祖先链布局变了。
