# 03 · handler 覆盖（用 154 帧做回归）

**目标**：把已经解出来的规则，变成核心里**能应答**的 handler。这是“从纸上对字节”走到“能顶上去应答”的那一步。

---

## 1. 真值在哪

`docs/evidence/frames-154.json` —— 154 帧整帧真值，两局抓包（局 A 56 帧、局 B 98 帧），每帧含：

| 字段 | 含义 |
|---|---|
| `header_hex` | 10 字节帧头 |
| `payload_hex` | 线上载荷 |
| `body_hex` | 身体层真值 |
| `frame_hex` | 线上整帧 |
| `seq / dir / plen` | 定位用，**seq 会重号，不能当主键** |

已验证：整帧 = `[u32 LE plen][i32 LE -plen][u16 LE 0x7fff][载荷]`，`载荷 = body XOR KEY[i%30]`，154/154 帧可重建（0 差异，286,157 B 全等）。

## 2. 已经能应答/能编的

| 层 | 状态 |
|---|---|
| 报到层 `wrap/unwrap` | 已实现（`rust/v50_payload.rs`），5 项真实样本测试 |
| 登录 body（proc 1） | 已实现（`rust/v50_login.rs`），70→72 B 逐字节断言 |
| 账号段编码（329 B） | 已验证（0 差异），**尚未进核心** |
| 帧头写出 | **尚未进核心** ← 第一件活 |

## 3. 任务，按顺序

**H1 · 帧头进核心（半天）**
- 新增 `write_frame_v50(body) -> Vec<u8>`，规则见 §1。
- 夹具用 `frames-154.json` 全 154 帧。
- 判据：154/154 帧 `frame_hex` 逐字节相等；负对照改 1 字节必须报 1 处差异。

**H2 · 账号段编码进核心（1 天）**
- 把 329 B 编码器写成 Rust（`v50_snapshot.rs`），输入 36 条 `(uid, tid, exp, level, max_level, reset_count)`。
- 判据：与 `frames-154.json` 里那两条 1400 帧的 `[30075, 30404)` 段逐字节相等。

**H3 · 按 proc 铺 handler（大头，估 12–20 个）**
- 先做**只读**的几个（解码并打日志，不做应答）：1003、1004（请求）、3452、10000、30004 心跳。
- 再做应答（先 1003、10000 这种小体量的，最后碰 1400）。
- 判据（每加一个 handler 都要跑）：
  1. `cargo test` 全绿；
  2. `frames-154.json` 回归不退化；
  3. 新增 handler 对应的帧，产出与 `frame_hex` 0 差异。

**H4 · 未知 proc 登记**
- 遇到没解出的 proc，只登记，不猜：`proc 号 / 方向 / 长度 / 首 16 字节 / 出现次数`。

## 4. 交付

- 每个 handler 一个测试，测试名写清 proc 与方向。
- 一份 `docs/handler-coverage.md`：proc → 已实现/只读/未知 三态表。
- 一份 `UNKNOWN.md`：没解出的 proc 及观察到的特征。

## 5. 别做

- 不要用“我自造请求→我自造应答，两边相等”当绿。
- 不要在没对真值之前改 `frames-154.json` 的任何一帧。
- 不要为了通过而放宽判据（尤其不要改成“差异小于 N 字节算过”）。

## 6. 推荐模型与推理强度

**GPT-6.2 Astra，推理强度拉满。** 理由：handler 是一个个独立小函数，最容易出现“单个都对、串起来漏一个”；而第 3 条判据（回归不退化）必须每次全量跑，不能抽样。
