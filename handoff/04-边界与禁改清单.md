# 04 · 边界与禁改清单

接手方开工前必须过一遍。这里的每一条都是踩过的坑，不是理论风险。

---

## 一、允许改的

| 范围 | 说明 |
|---|---|
| `F:\Codex\tfd-offline-2\app\` 内 | Rust 核心（`rust/`）、测试（`tests/`）、入口（`tools/`）、契约文档（`V50-*.md`）。改动前先建分支 |
| 本包 `handoff/` 下 | 只读。要写结论就写在你自己工程的 `docs/` 里，不要回写本包 |
| 存档副本 | 允许读；要写就把 `characters.sqlite3` 复制一份再写，**永远不动原件** |

## 二、绝对不能碰的

1. **不写内存猜偏移。** 向 `[账号消息+0x68/0x70/0x74]` 写角色条数或合成角色行，两次实验都在约 26 秒触发客户端 `exit_code 3`。这条路已证伪并回滚，不要再试。
2. **不改原档。** `characters.sqlite3`（36 角色 / 2.39 MB）是唯一真档，备份哈希 `AA5ACB84…`。只读，或写副本。
3. **不动 `patch_v50.py` 的行为开关。** 里面的 `TFD_*` 实验开关（`TFD_FORCE_INT64` / `TFD_DROP_TOPFIELD` / `TFD_TRIM_CHAR` / `TFD_TRIM_COUNT` 等）只用于诊断，不要留在默认路径上。
4. **不动注册表、系统安全设置、防火墙、驱动。** 需要任何提权或系统级改动，先停下来要授权。
5. **不发布、不分发、不上传任何资产、不提供对外下载。** 本包是本地研发验证用。
6. **不跨模块并行硬推。** 依赖链是 `M00 → M01 → M02 → M03 → M04`，前一环没绿，后一环的绿是假的。

## 三、失败怎么回滚

- **代码**：一域一分支，一次提交只做一件事。失败就 `git checkout` 回上一个绿点，不要在坏状态上继续加改动。
- **存档**：写副本；出错就删副本重来，原档不动。
- **配置**：改 `patch_v50.py` 之类文件前先 `cp` 一份带后缀的备份（如 `.bak-<日期>-<原因>`），回滚就是换回来。
- **台账**：每次失败在 `docs/` 记一条——做了什么、看到什么、结论"证伪/未定"。不做记录等于下一轮重新踩。

## 四、遇到这些情况要停下来问，不要自己决定

- 判据本身跑不通（不是代码错，是判据写错了）→ 停下来说，不要改判据凑绿。
- 需要真实客户端字节，而手上样本是被截断的（`03-考卷样本.json` 里带 `res_err` 的三条）→ 不要用截断数据反推完整格式。
- 需要开游戏才能验证 → 这活不在本包范围内，交回主开发侧。
- 发现资产 sha256 与 `01-资产清单.json` 对不上 → 版本已漂移，停下来核对，不要在旧版本上开工。

## 五、无人值守时的自律条款

- **无变化就安静**：只在有实质结果、明确失败、或需要人工时输出，不做过程播报。
- **不等人**：未知规则记进待办，继续往下做，不阻塞在某个问题上。
- **有止损点**：到点就收工，把已完成与未完成分开写清楚，不留半成品状态。
- **不做的事**：不因为"想推进"就放宽判据，不因为"想通过"就去动被禁改的东西。
