# 02 · 存档往返（21 张表）

**目标**：核心能读出存档、改完写回、再读一次逐字段相等。做到这一步，才谈得上“我们自己维护角色”。

---

## 1. 真值在哪

```
E:\第二后裔\TFD发布端V50\TFD发布端V50\data\launcher\saves\04f2858b03d3e1f379515d84ba575f03\characters.sqlite3
```

- 大小 2,392,064 B，旁边有 `-wal`（24,752 B）与 `-shm`。
- 表结构：**21 张表**；`characters` 36 行，`accounts` 1 行，`account_collections` 28 行，`local_mission_receipts` 141 行。
- `characters` 列：`uid, account_uid, template_id, exp, level, max_level, reset_count, state_json, revision, updated_at`。
- `account_character_selection = 35`（当前选中角色）。

**必须只读打开**：`sqlite3.connect('file:...?mode=ro', uri=True)`。

> **踩过的坑（务必避免）**：不要加 `immutable=1`。它会**忽略 WAL**，导致只看到 1 张表、误判“36 行不存在”。36 行就在 WAL 里。本任务只读副本，允许读 WAL（`mode=ro` 默认会读）。

## 2. 已经解出来的部分（可以直接用）

线上账号段（`proc 1400` 应答里的 329 B）已经破解：

```
[2×uid 1B][template_id u32 LE][2×exp][2×level][2×max_level][2×reset_count]
```

- 变长整数：最高位 `0x80` 是续位；数值一律 **×2** 存。
- 段范围：`[30075, 30404)`，36 条，可变长（9 B 占 32 条、10 B 1 条、11 B 2 条）。
- 六字段 36/36 与 sqlite 相等；编码器两帧 **0 差异**（含负对照）。

详见 `docs/evidence/v50_payload/provenance.json` 与 `tests/fixtures/v50_payload_sample.rs` 的同伴文件；GitHub 上还有一份《G1/G2 可判》报告。

## 3. 这一块要做的

1. **读**：把 21 张表全部读出来，输出稳定的中间结构（字段名 + 类型 + 行数），不要只读 `characters`。
2. **写回**：用同一份数据写一份**新库**（不要覆盖原件），再读回来。
3. **判据（硬）**：原件与写回件逐表、逐行、逐字段相等；浮点/文本按原样比（`state_json` 这类文本要逐字节相等，不许 parse 再 dump）。
4. **增量场景**：改 `characters` 某行的 `level` / `exp`，写回后读回，只有该字段变、其余字段与行数不变。
5. **与线上层打通**：把写回后的 36 行再编码成 329 B，与 `docs/evidence/frames-154.json` 里那两帧的账号段逐字节相等。

## 4. 交付

- `store_roundtrip.py`（或 Rust 实现，放 `rust/` 下）：`--check` 模式跑 1–4 全部判据。
- 一份记录：命令 + 输出 + 每张表的行数对照表。
- `UNKNOWN.md`：哪些表语义不清、哪些字段无法往返（例如带时区的时间戳、自增 id）。

## 5. 别做

- 不要移动/删除任何存档原件，也不要改 `-wal`。
- 不要用“我能读出来”当往返成功；必须“写回去再读出来还一样”。

## 6. 推荐模型与推理强度

**GPT-6.2 Astra，推理强度拉满。** 理由：21 张表的往返是长上下文的一致性任务，最容易出现“前面 18 张对、后面 3 张悄悄丢字段”；这类错误不会报错，只会让存档慢慢坏掉。
