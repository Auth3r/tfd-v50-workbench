## 0. 一句话结论

真正"从零、没有现成可复用"的只有两块：**内容包 `content.sealed` 的语义**，和**客户端 schema 到内存偏移的映射**。

## 3. 可以立刻交出去的活（带验收判据）

1. **帧层 + 登录**：用 `docs/考卷-协议样本-20261121.json` 与首帧样本做输入，跑 `tests/v50_codec.rs`、`login_procedure1.rs`，**判据 = 本地 `cargo test` 全绿、且解出的 proc/长度与样本一致**。
2. **账号快照 → 编码器**：输入 36 角色存档 + `M1AccountSimpleInfo` 35 属性 + `M1CharacterSimpleInfo` 13 属性（附录偏移表），输出可解码的应答字节。**判据 = 自编码后再自解码，字段与存档逐项相等**（这一条只证明自洽，不证明客户端认）。
3. **集合域铺开**：按 21 个 collection 的已打印 schema，一域一个 `run_<域>.py`。**判据 = 每域单测独立通过，不依赖客户端。**

> 这三件都不需要我，也不需要开游戏；额度用掉也是有效的。

## 4. 只有我能做、也是当前唯一卡点

**客户端到底怎么读这份账号快照。** 现在的事实是：服务端生成 36 条 → 同一条应答里夹带出网 → 客户端原生读数是 0 → 走创角。
卡点不在数据，在"字段/层级对不上"。要定位它必须：抓完整 `1004` 应答字节、在客户端侧对照解码结果、必要时看解码函数。这三步都要上机。

| 偏移 | 字段 | 类型 |
|---|---|---|

| 0x08 | CharacterTid | u32 |
| 0x0c | Level | u32 |
| 0x10 | MaxLevel | u32 |
| 0x14 | EigenFactorLevel | u32 |
| 0x18 | Favorites | bool（1 字节，0x19–0x1b 为填充） |

| 0x30 | CustomizeOptions | 数组 |

`M1AccountSimpleInfo`（280 字节，35 属性）关键偏移：`Uid`0、`Name`8、`WearingList`64、**`CharacterList`104（即 0x68）**、`SelectedCharacter`120、`CustomizeList`200、`FellowList`**224（即 0xE0）**、`SelectedVehicle`240、`VehicleList`248。
> 注意：桥一直读的 `+0x70` 是 `CharacterList` 的条数字段没错，但它在实际拿到的对象上取到的是无效值——这一点已实测，勿再据此写内存。
