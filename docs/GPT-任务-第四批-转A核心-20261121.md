## 一、这轮为什么转 A（你必须知道的前置事实）

A 的目标是让客户端不再走创角分支。我们已在真机上做过三条 **写库实验**，全部否定，说明客户端那个"角色数"**不是查库得来的**：

| 实验 | 写入内容 | 结果 |
| --- | --- | --- |
| 改 `local_runtime.sqlite3` 角色行 `state_json` + `revision` | `{"InitialDefaultPlayerSetId":106100003}`，revision 0→1 | `character_count` 仍 0，已按 sha256 原样回滚 |
| 向 `saves\1\characters.sqlite3`（数字账号目录）写角色 | uid1/acc1/template 101000003/level1 + selection(1,1) | `character_count` 仍 0，已回滚 |
| 按宿主二进制里的旧全局路径 `data/characters.sqlite3` 放一份带角色的库 | 167,936 B，含 demo uid1 + 1 角色 + selection + 14 集合 | `character_count` 仍 0（37.6 s 慢档，无 `native_title_creation_error`），已清理该文件 |

三条实验期间，`04f2…/characters.sqlite3`（1 角色 / selection (1,1) / 14 集合）与 `local_runtime.sqlite3`（1 角色 / selection (1,1) / 152 条会话全部 account_uid=1）**始终没被改空**，读后仍各有 1 行角色。→ **库里一直有角色，客户端一直读 0。**

已确认的相关事实（不要重复推翻）：

- 客户端那个值来自桥 hook `base.add(0x44a5370)` 返回后读 `a[1].add(0x70).readS32()`，是**内存值**，不是 SQL 结果。
- 宿主 `unpacked/client.dll` 里确有 `SELECT count(*) FROM characters WHERE account_uid=?`、`SELECT c.uid,c.template_id,c.level FROM characters c JOIN account_character_selection s ...`、`has_characters`、`character_count`、`list_characters`、`_characters_tab` 等明文串，但这些串**只证明宿主具备这些查询能力，不证明它在这条链路上用了它们**。
- 启动器界面上"有 1 个角色"，是启动器读自己那份库的显示，和客户端内存里的 count 不是同一个来源，不能用它当"服务端回了角色"的证据。

结论：**A 的缺口在"登录后这条应答里到底装了什么"，不在数据库。** 所以本轮全部是协议侧取证。

## 二、P5 账号-角色列表契约（继承第三批未交付的 P2）

**目标**：写出一份"登录 → 账号同步 → 角色列表"的**过程级契约**，让实现侧知道宿主必须回什么、字段长什么样。

**输入**：`unpacked/assets/network-expansion.json`（36 过程 / 162 schema）、客户端实际调用的过程号（`1`、`1003`、`1004`、`1010`、`1012`、`1400`、`2006`、`3452`、`10000`、`30001`、`30004`、`20000`）、以及你手上的 V50 帧样本。

**必须回答的四件事**：

1. 哪个过程承载**账号身份/登录态**，哪个承载**角色列表**，哪个承载**当前选中角色（roster 选中项）**。允许给候选，每个候选必须写明判据。
2. 角色列表条目是**数组**还是**按 uID 索引的映射**；单条目里是否同时带 `template_id` 与 `level`、是否带 `state_json` 类扩展块。
3. 是否存在一个**显式的 count / 数量字段**，以及它与数组长度是否可能不一致（客户端若读的是"字段值"而不是"数组长度"，两者不同就会直接读 0）。
4. 客户端把 0 判成 `creation_required` 的判据，按静态结构能推到哪一层；推不到的写 `unverified`。

**输出格式**：一张表，列 `过程号 | 方向 | body 结构名 | 字段 | 类型 | 是否数组 | 证据等级 | 判据一句话`。证据等级只用三档：`schema声明` / `帧字节命中` / `unverified`。

**禁止**：把"结构里存在某字段"写成"该字段在运行时有值"。

## 三、P6 在 136 分片语料里定位并解码登录首批应答

**目标**：用现有语料直接回答一句话——**宿主回给客户端的这条应答里，有没有角色条目。**

**语料**：`E:\第二后裔\TFD发布端V50\TFD发布端V50\docs\抓帧流水-原始分片-20261121.jsonl`（136 条 send/recv 原始分片，112,092 B）。你自己的归并脚本已把它划成 42 个 `0x7fff` 帧 + 3 个总长型候选 + 31 条 TLS 记录 + 4 个 HTTP 报文 + 1 段 296 字节未划界。

**做法**：

1. 先按时间序把"登录完成后的前若干帧"挑出来（过程号来自帧体，或按长度/方向/相邻关系先做候选分组；分组是候选就必须标注）。
2. 对挑中的帧，用 P5 的契约做逐字段解读：帧内偏移、字段名、值、单位。字段解不出来就停在字节边界，不要用猜测填空。
3. 给出结论三态之一：**有角色条目 / 明确没有 / 无法判定**。选"无法判定"必须写清缺哪一段字节或哪个字段边界，并给出行号。

**必须交付的复核手段**：一条能重跑的命令，以及该命令输出里可对照的行号 + 字节偏移。判据不能只靠叙述。

**已知限制**（不要当成你的过错，但要写进产物）：JSONL 没有 socket ID 与连接生命周期，连接归属本来就是推定；第 4 行 296 字节缺可验证边界。

## 四、P7 `characters` 表 ↔ 客户端角色结构绑定

**目标**：回答"宿主若真要回角色，**最少**必须回哪几个字段才能被客户端接受"，把每个字段的绑定打到行级。

**输入**：`V50-SAVE-MAPPING.md` 里已读过的列（`characters.uid / template_id / level / exp / max_level / reset_count / revision / state_json / updated_at`，`account_character_selection.character_uid`）、`V50-CLIENT-TABLE-BINDINGS.md` 的 36 个角色模板与 `M1PlayerData`、以及 `network-expansion.json` 里的角色相关结构。

**必须回答**：

1. 角色条目里 `template_id` 与 `level` 是否**同一条目内**出现，还是分散在两个不同应答里（后者会让"只回 template 不回 level"的实现在客户端侧表现为空）。
2. `state_json` / 扩展块在结构里对应哪个字段，**空 `{}` 是否合法**，为空时客户端会当成"未完成角色"还是"默认角色"。这条直接决定我们改库方向对不对。
3. `revision`、`reset_count`、`exp` 中哪些是**必需**、哪些是可缺省；缺省时客户端按什么默认。
4. 给出"最小合法角色条目"的字段清单，每项标 `verified / 候选 / unverified`。

**要求**：所有跨构建结论保持 `unverified`；只有同一来源能串起来（表行 + 结构声明 + 帧字节）才可升为 `verified`，并在产物里贴出行级引用（表名、row_key 或 template_id、字段路径）。

## 五、P8 抓帧规格（条件任务，P6 判不出时才做）

若 P6 只能给出"无法判定"，输出一份**下一次抓帧的最小规格**，我们要照着它抓一局：

- 要哪几个过程号的**完整请求与应答配对**（不是单方向）。
- 起止条件（从登录成功那一刻开始，到第一次出现创角相关事件为止）。
- 每条记录必须带的元数据：方向、时间戳、**socket 句柄或连接序号**、过程号（若已知）、原始字节、以及"该记录属于第几次 recv/send"。
- 判定标准：拿到几对、满足什么条件就能把 P6 的"无法判定"变成二选一。

注意：这条规格要写成**我们这边能直接执行**的形式，不要写成"建议补充更多样本"这种无法落地的表述。
