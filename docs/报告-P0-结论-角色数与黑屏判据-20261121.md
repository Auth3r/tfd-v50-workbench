# 报告 · P0 结论：0 角色不是病，黑屏判据在别处

日期：2026-11-21 · 依据：桥代码原文、本局事件日志、前人成功局档案 · 未改任何代码

---

## 一、结论（三条）

1. **`character_count: 0` 不是故障，是这版客户端的正常表现。**
2. **黑屏的真正判据是 `native_title_creation_error` 有没有出现**：出现 = 客户端自己的标题/创角流程还在跑（画面正常）；不出现 = 桥把流程接管了、没人驱动（纯黑）。
3. **"存档里有 1 个角色、客户端读到 0 个"这个矛盾是我之前读错了字段来源**，不是数据问题。

---

## 二、证据链

### 2.1 `character_count` 是客户端内存里的值，不是查库结果

桥文件 `offset_rework\old_bridge_v30_bt.js`：

```js
attachSafe(base.add(0x44a5370), {
  onEnter(a) { this.count = a[1].add(0x70).readS32(); },
  onLeave() {
    report('native_account_loaded', {character_count: this.count, creation_required: this.count === 0});
  }
});
```

即：**在客户端某个函数返回时，读它参数对象 `+0x70` 处的 i32**。这个值反映的是"客户端解析完账号响应后，自己内存里认为有几个角色"，与服务端数据库没有直接关系。

### 2.2 `bridge_ready` 里的 `existing_character: true` 是写死的票据常量

桥文件第 1 行：

```js
const LAUNCH = {"ticket": "...", "existing_character": true, "account_uid": "1", ...};
...
report('bridge_ready', {character_creation_bypassed: false, existing_character: LAUNCH.existing_character});
```

所以它恒为 `true`，**不能拿它和 `character_count` 对比**。我此前把这两条当成"桥说有角色 / 服务端说 0 个"，是误读。

### 2.3 前人成功局就是 `count = 0` 进游戏的

`offset_rework\REPORT-2026-11-20-进游戏成功-复现配方.md` 记录的成功链路原文：

```

75.286  native_creation_confirm_clicked          ← 用户点创角确认
```

**`count=0` → 走创角 → 注册成功 → 进世界。** 该报告还写明："真档 36 角色 → 新版读成 0 → 走创角，符合预期"。

### 2.4 本局属于"应出画面"的那一类

本局 run `20261120T114527-1aae5c`：

| 时间 | 事件 |
|---:|---|
| 1.645 | `game_process_started` |
| 2.038 | `bridge_ready` |
| 5.735 / 11.268 | `local_platform_config` |
| 24.981 | **`native_title_creation_error`**（access violation 0xffffffffffffffff） |
| 24.981 | `native_account_loaded` `character_count: 0` |

**`native_title_creation_error` 出现了** → 按 2.3 的判据，这一局是**能出创角界面**的。我在 25 秒时主动 `WM_CLOSE` 收工，因此**没有观察到画面**——不是它黑了，是我提前关了。

## 五、给成员的对齐要点（避免把 0 角色当成 bug 去修）

- `character_count: 0` 是**预期**，不要去"修成 1"。
- 判黑屏只看一条：**有没有 `native_title_creation_error`**。
- 任何"角色数来自哪个库"的推断都要先核对桥读的是哪个内存偏移，别再从数据库反推。
