# 决策 · 宿主运行时的替换路径、顺序与风险

日期：2026-11-21 · 状态：讨论结论，未动代码
背景：界面层要换成自研；同时对“宿主运行时”有洁癖（不希望长期依赖第三方产物）。

---

## 0. 术语表（先看，避免误读）

| 词 | 本文含义 |
|---|---|
| **宿主** | `TFDLauncher.exe` + `unpacked/client.dll` 组成的本机运行时进程。**不是 Docker、不是虚拟机** |
| **兼容桥** | 仓库内 `offset_rework/old_bridge_v30_bt.js`，在客户端进程内补齐启动回调（`platform_config` / `title_creation` / `account_load`）。**不是第三方工具** |
| **启动驱动** | “谁拉起客户端、谁维持会话生命周期”这件事 |
| **内容层** | 36 个过程（任务/商店/邮件/实例/活动…）的业务应答实现 |
| **本地会话初始化** | 宿主启动前准备数据目录、会话、账号状态的步骤（此前文档里叫“启动脚本那一套”） |

---

## 1. 结论先行

1. **“不可或缺”这个说法要收回**。准确表述是：**宿主是目前唯一验证过的启动路径**，不是物理上不可替代。
2. 宿主拆开是三块：**界面 / 内容层 / 启动驱动**。第一块已在替换，第二块有人在做，第三块还没验证。
3. **“把内容答案算完”和“换掉启动驱动”是两个账本**，不能互相抵扣。
4. 换壳之后还需不需要本地会话初始化，**取决于宿主还在不在**：在 → 需要；去掉（第三刀成功）→ 整个步骤消失。

---

## 2. 宿主到底提供了什么

| 块 | 具体内容 | 现归属 | 可替代性 |
|---|---|---|---|
| ① 界面与编排 | 主窗、启动校验提示窗、推广窗、按钮 | 自研壳 | 已可替代（只差一行调用） |
| ② 内容层 | 19 张表、36 过程处理、`account_collections` 14 键 | 自研服务端 | 可替代；前提是接住 `1 / 2010 / 30004` |
| ③ 启动驱动 | 拉起客户端 + 加载兼容桥 + 维持会话 | 宿主 | **唯一未被验证的一块** |

关键事实：**③ 已经有一半被替换了**。兼容桥在客户端进程内补三个启动回调，这部分原本是宿主的职责。剩下未替代的只有“谁拉起进程、谁维持它活着”。

---

## 3. 三刀切法

```
第一刀：界面      → 自研壳（已基本完成）
第二刀：内容层    → 自研服务端（并行进行中，通过连接地址参数指向它）
第三刀：启动驱动  → 极薄启动器（只拉起进程）+ 已有桥（未验证）
```

### 第三刀的判据（只有一条）

**外部拉起客户端 + 立即加载兼容桥 → 客户端是否活过 60 秒、出现标题页、持续发送 `30004`。**

- 成立 → 宿主可去掉，“一个几十行的启动器 + 已有桥”即可闭环；
- 不成立 → 宿主保留，但能明确卡在哪一步（加载时机 / 初始化顺序 / 会话维持）。

历史教训：早期“裸启 15 秒自退”的结论来自**没有加载桥**的裸启，不能直接用来否定“外部拉起 + 桥”。

---

## 4. 第三刀实验规格（交给执行方，不改任何现有文件）

**目标**：验证“无宿主 + 外部拉起 + 桥”是否能活。

**步骤**
1. 先记录当前可用基线：宿主路径下的一局正常局（`native_title_creation_error` 出现、`native_account_loaded ≈ 24s`）。
2. 外部拉起客户端进程，命令行沿用现有等价参数（连接地址指向自研服务端）。
3. 进程起来后立即加载兼容桥，**沿用仓库内现有加载机制**，不重写桥代码、不改加载方式。
4. 观测 90 秒，记录：进程是否存活、`bridge_ready` 时间、是否出现标题页事件、是否发出 `30004`、是否出现窗口。

**判据**

| 结果 | 含义 |
|---|---|
| 存活 > 60s 且出现标题页 | 第三刀成立，宿主可去 |
| 15 秒内退出 | 加载时机赶不上初始化，或仍有宿主隐含的初始化步骤 |
| 存活但零连接 | 客户端没到连接阶段，或地址参数未生效 |

**约束（重要）**
- 不改桥代码、不改宿主文件、不改客户端文件、不改仓库内已跑通的启动脚本；
- **失败即停**：15 秒自退判定为“宿主暂不可去”，最多重试一次，不做进一步侵入性尝试；
- 全程日志落盘，便于与基线比对；
- 本实验只证明“能拉起 + 能连上”，**不证明内容正确**。

---

## 5. 先做内容、后换驱动：七条风险与缓解

| # | 风险 | 为什么会出现 | 缓解 |
|---|---|---|---|
| 1 | 契约漂移 | 内容层按当前应答语义写死（旧版答案），换驱动后字段与顺序不一致 | 内容层写成**纯 handler**：`def handle(ctx, req: bytes) -> bytes \| None`，不依赖宿主内部对象 |
| 2 | 状态归属混乱 | 图快直接读宿主内部会话对象 | 只通过自有数据库 + 进程边界访问；**禁止 import 宿主模块** |
| 3 | 时序假设固化 | 写成“客户端 X 秒内一定连上”，换驱动后时序变了 | 一律**事件驱动**（等连接事件再算），不写死秒数 |
| 4 | 端口/地址漂移 | 宿主固定端口，内容层跟着写死 | 端口进配置文件，单一来源 |
| 5 | 存档双写 | 宿主 19 表 与 自研 snapshot 混用，互相覆盖 | **单一归属**：切换期间宿主只读、自研服务端独占写入；切换完成后不反转 |
| 6 | 回归面膨胀 | 每个功能只在宿主环境下验证过 | 维护回归脚本（清单见 `CONTRACT.md` §8），每次提交都跑 |
| 7 | 团队图快 | 多人分工时有人直接摸宿主内部 | 评审红线：**改动了宿主内部接口的 PR 一律退回** |

**结论**：顺序不是问题，**耦合才是问题**。只要内容层始终“只吃字节、只吐字节、只碰自有状态”，后面换驱动只是换一层皮；一旦有人为快直接摸宿主，成本就从“换驱动”变成“重写内容”。

---

## 6. 两笔账：答案 vs 驱动

| 账本 | 内容 | 什么时候不再需要宿主 |
|---|---|---|
| 答案（内容层 36 过程） | 任务、商店、邮件、实例、活动… | 答案写对之后，不再需要它“替我们答” |
| 驱动（谁把客户端拉活） | 拉起 + 三个启动回调 + 会话维持 | 只有第三刀成功，才不再需要它“替我们起” |

- 答案全对，客户端照样可能起不来 → 驱动这本账独立存在；
- 驱动换成几十行启动器，答案错还是会被客户端断开 → 答案这本账也独立。

---

## 7. 换壳之后，还要不要本地会话初始化

| 形态 | 还要不要 | 原因 |
|---|---|---|
| 宿主保留 | **要** | 会话与账号状态的准备在宿主进程内部完成，自研壳只需调用现成启动命令；用户体验上不出现任何提示窗口 |
| 第三刀成功（宿主去掉） | **不要** | 没有任何组件在校验，自己拉起进程即可，这个步骤整体消失 |

所以这一步不是永久步骤，它是**宿主存在的附属品**。洁癖的痛点在第三刀解决，不在界面。

---

## 8. 仓库卫生（不靠自我说服，靠工程边界）

1. **仓库不放第三方二进制**：`TFDLauncher.exe`（111 MB）、`client.dll`、`content.sealed`、运行时依赖库一律不进 Git（其中启动器还超单文件 100 MB 限制）；
2. **脚本只引用外部路径**：base / repo / user 三类组件分离（见 `CONTRACT.md`），仓库里只有自研代码；
3. **写清来源与使用声明**：README 如实说明“运行时来自用户本地安装”，不打包、不分发；
4. **可替换性本身就是最好的辩护**：结构上“随时能换掉第三方组件”，比任何声明都有说服力。

---

## 9. 建议的执行顺序

1. **先做第三刀实验**（1 小时，零风险，不改任何文件）——它决定洁癖问题是现在解决还是半年后解决；
2. 实验成功 → 自研壳直接对薄启动器，宿主退出流程；
3. 实验失败 → 壳走“宿主后台无窗口”形态，同时把“内容层纯 handler 化”作为硬约束推进；
4. 内容层与第二刀并行，不看驱动这本账的脸色。

---

## 10. 四个最容易误读的点

1. **宿主 ≠ Docker**。它就是一个 Windows 进程，装着 `client.dll` 和客户端。
2. **兼容桥 ≠ 第三方工具**。它补的是启动回调，让客户端能走到登录阶段；不修改游戏逻辑、不读写内存里的数值。
3. **内容层 ≠ 服务端**。内容层是 36 个过程的应答实现；服务端还包括传输、会话、状态存储。
4. **启动驱动 ≠ 协议**。协议对了但驱动不对 → 零连接；驱动对了但内容不对 → 连上后被断开。
