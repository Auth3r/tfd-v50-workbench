## 三、本批任务

### P0（最高优先）· 载荷性质判定：加密 / 压缩 / 明文编码

输入（全部离线，不需要客户端）：

- 一条 35 字节真实首帧：
  ```
  19 00 00 00 e7 ff ff ff ff 7f 23 a2 f7 57 44 28 22 20 0f 38 00
  11 24 2c 3b 65 59 5f 36 39 1e 4a a9 ee 14
  ```
  已知：`0..3` 小端 = 25（= 35 − 10），`4..7` = −25，`8..9` = `0x7fff`，载荷 = 后 25 字节。
- 帧流水里另有 87 条入向帧（长度与时间分布已知）。

要做的事：

1. **熵与分布**：对载荷字节做字节值分布、重复率、块内自相关，判断"高熵随机"还是"低熵结构"。
2. **长度关系**：改造 `19 00 00 00` 这个长度字段是否与某条已知结构（25 字节）存在整除/固定填充关系。
3. **已知明文对照**：若怀疑是加密，用已知的协议常量（过程号、`0x7fff` 标记）去尝试定位是否在明文里出现。
4. **结论三选一并给证据**：`encrypted` / `compressed` / `plain-encoded`；都不确定就输出 `undetermined` + **明确列出还需要哪一种样本**（例如：同一过程两次调用、不同长度同级帧、有应答的完整往返）。

**禁止**：不要为了"看起来解开了"而拼一个自洽的字段表。这条请当硬约束。

### P2 · `V50-ACCOUNT-LIST-CONTRACT.md`

把"最小可行的角色列表响应"写成规格：

1. 一个角色需要哪些字段（模板 ID、名字/字符串键、等级、上限等级、uid、创建时间），逐项标注"有证据 / 无证据"。
2. 与已核实的 36 个角色模板、40 级等级表对齐（这两张表已经有行级数据，可以直接引用）。
3. **验收口径写明**：客户端侧的观察点是 `native_account_loaded` 的 `character_count`，从 0 变 ≥1 才算过。

### P3 · account_save 域升成纯函数（Sol + 中做）

- 编码一律标 `synthetic`，**不得声称已对接真实 codec**
